# Разбор дефектов hw3-broken

Пять намеренных дефектов. Для каждого: в чём был, как проявлялся, как исправлен
и каким числом это подтверждается.

Числа в блоках «Подтверждение» снимаются с реального прогона:
`make check`, `make v1`, `make v2`, `make diff`.

---

## Дефект 1. Данные уезжают в git, а DVC их не видит

**В чём был.** Три вещи сразу, и все про одно:

1. в корневом `.gitignore` не было `data/` — `git add .` забирал `raw.jsonl`,
   `clean.jsonl`, `train/val/test.jsonl` в индекс;
2. в `.dvc/config` не был объявлен ни один remote — выгружать данные было
   некуда, то есть DVC версионировал их только локально;
3. в `dvc.yaml` у стадии `split` в `outs` был объявлен только `data/train.jsonl`.
   `data/val.jsonl` и `data/test.jsonl` не были артефактами пайплайна вообще:
   они появлялись на диске как побочный эффект и не попадали ни в `dvc.lock`,
   ни в кеш. Откат `dvc checkout` их не восстанавливал.

**Как проявлялся.** `git log --stat` после первого же коммита показывает
крупные JSONL. Проверка 1 в `make check` красная по трём пунктам из четырёх.
Отдельно неприятно, что пункт 3 не имеет симптомов до момента, когда сплит
понадобится восстановить: тогда `test.jsonl` просто не окажется в кеше.

**Как исправлен.**

- корневой `.gitignore`: добавлены `data/`, а заодно `.venv/`, `__pycache__/`,
  `*.bak`, `*.orig`, `.DS_Store` (проверка 8 — гигиена);
- `dvc remote add -d local ../hw3-dvc-storage` — локальный remote вне
  рабочего дерева репозитория, чтобы он сам не попал в `git add .`;
- в `dvc.yaml` у стадии `split` в `outs` добавлены `data/val.jsonl`
  и `data/test.jsonl`; у стадии `collect` добавлен `metrics/collect.json`.

**Почему именно так, а не «удалить файлы из индекса».** Один раз закоммиченный
JSONL остаётся в истории навсегда: `git rm --cached` убирает его из рабочего
дерева, но не из объектов. Репозиторий продолжает клонироваться вместе с ним.

**Подтверждение.**

```
1. Данные не в git и под управлением DVC
  ✓ git не отслеживает ни одного файла в data/
  ✓ data/ перечислен в .gitignore проекта
  ✓ remote DVC настроен: local .../hw3-dvc-storage (default)
  ✓ все артефакты из params.paths объявлены в outs dvc.yaml
```

## Дефект 2. Смена версии данных не пересчитывает пайплайн

**В чём был.** У стадии `collect` в `dvc.yaml` не было ни секции `params`,
ни зависимости от самих данных источника:

```yaml
collect:
  cmd: python -m src.collect
  deps:
    # TODO: добавить сюда путь к СВОЕМУ источнику данных.
    - src/collect.py
    - src/config.py
  outs:
    - data/raw.jsonl
```

`collect.version` живёт в `params.yaml`. DVC пересчитывает стадию, когда
изменился хоть один её `dep` или хоть один объявленный `param`. Здесь не было
объявлено ни того, ни другого: файл `params.yaml` менялся, а для стадии
ничего не менялось.

**Как проявлялся.** `python scripts/set_version.py v2 && dvc repro` отвечает,
что пересчитывать нечего. `data/raw.jsonl` остаётся от v1, а метрики
и `dvc metrics diff` показывают разницу между версиями как нулевую —
то есть врут ровно в том месте, ради которого затевалось версионирование.

**Как исправлен.** В стадию `collect` добавлены:

```yaml
    deps:
      - data/source        # сами шарды источника
      - src/collect.py
      - src/topics.py
      - src/config.py
    params:
      - collect            # вся секция: version, n_rows, фильтры, промпты
      - paths.raw
```

Секция целиком, а не `collect.version` поштучно: менять `max_per_topic`
или `verify_output_syntax` и не пересчитывать стадию — тот же дефект,
просто с другим параметром. Заодно у `clean` добавлен `paths.raw`,
у `split` — `clean.near_dup` (стадия им пользуется, значит, зависит от него).

**Подтверждение.**

```
4. Смена версии данных реально пересчитывает пайплайн
  ✓ clean.jsonl пересчитан: v1 a224ec41 (1812 строк) → v2 57d154a3 (2184 строк)
```

И то же самое через `dvc metrics diff` после коммита v1:

```
metrics/collect.json    files          1       2       1
metrics/collect.json    rows_scanned   9252    18612   9360
metrics/collect.json    rows_written   1812    2184    372
metrics/collect.json    version        v1      v2      -
metrics/clean.json      rows_out       1810    2174    364
```

Колонка `Change` — это и есть доказательство, что стадия переисполнилась,
а не отдала артефакт от прошлой версии.

## Дефект 3. Контаминация train/test

**В чём был.** Два независимых промаха в `src/split.py`.

*Первый — ключ разбиения.* Функция `row_split` раздавала метки `train/val/test`
**строкам**: перемешивала `range(count)` и резала по долям. Группа при этом
рвалась пополам.

*Второй — реакция на находку.* Стадия честно считала `report(...)`, клала
результат в `metrics/split.json` и завершалась с кодом 0 независимо от того,
что там было. Проверка, которая никогда не падает, — украшение.

**Как проявлялся.** `scripts/check_contamination.py` находит пересечения
train↔test: один и тот же вопрос или его парафраз по обе стороны. При этом
`dvc repro` зелёный. Симптом утечки — не ошибка в логе, а метрика на test,
которая вас приятно удивила.

**Почему группа, а не строка.** В источнике задания массово парафразны:
«напиши функцию сортировки списка» встречается в десятках формулировок.
Случайный сплит раскладывает парафразы по разные стороны с вероятностью,
близкой к единице. Лекционный замер: случайный сплит — 19,5% утечки в test,
сплит по темам — 12,3%, дедупликация плюс группы — 0. Ноль получается только
после того, как одинаковое уже схлопнуто, — поэтому дефект 3 не чинится
без дефекта 4.

**Как исправлен.**

- `row_split` заменён на `group_split`: неделимая единица — группа
  (`split.group_key = topic`). Группы идут от крупной к мелкой и попадают
  туда, где сейчас наибольший недобор строк; порядок равных по размеру групп
  фиксирован `split.seed`, чтобы добавление шарда в v2 не перетасовывало темы;
- если какой-то сплит остался пустым (групп меньше, чем частей), стадия падает
  с объяснением, а не отдаёт пустой `test.jsonl`;
- в конце стадии — гейт: `is_clean(rep)` ложно ⇒ `SystemExit` с перечислением
  всех четырёх счётчиков и примерами пар.

**Подтверждение.**

```
train: 1448 строк, test: 181 строк
  пересечение по id:        0
  пересечение по тексту:    0
  пересечение по группам:   0
  near-dup пар train↔test:  0
контаминации нет
```

## Дефект 4. Дедупликация только точная

**В чём был.** В `src/clean.py` пятым шагом стояла заглушка:

```python
    # 5. TODO: сюда просится ещё один шаг дедупликации.
    near: set[int] = set()
```

`near_duplicates` из `src/dedup.py` был написан, покрыт комментариями
и ни разу не вызван. Метрика `dropped_near_dup` при этом существовала
и всегда равнялась нулю — то есть отчёт выглядел исправным.

**Как проявлялся.** Пара «тот же вопрос, переставленные варианты ответа /
другие пробелы / другая нумерация» переживает очистку и остаётся в датасете
дважды. Точный хэш их не видит: тексты различаются побайтово. На лекции на
курсовом датасете точная дедупликация нашла 0 дублей, а сравнение
нормализованных вопросов — 11 626.

Второе следствие важнее первого: пережившие очистку парафразы — это готовое
сырьё для контаминации train/test (см. дефект 3).

**Как исправлен.** Шаг 5 вызывает `near_duplicates` по тому же ключу, по
которому работает точная дедупликация (`normalize_text(ex.user)`), с
параметрами из `clean.near_dup`: шингл 4 слова, 64 перестановки MinHash,
порог Жаккара 0,85.

Три детали, которые здесь не случайны:

- **порядок.** Схема → длины → ПДн → точная → near-dup. ПДн строго до
  дедупликации: две строки, отличавшиеся только телефоном, после маскирования
  становятся одинаковыми и обязаны схлопнуться. Точная строго до near-dup:
  дешёвая операция снимает массу, дорогой MinHash работает по остатку;
- **один ключ на оба шага.** Если точная дедупликация и near-dup нормализуют
  текст по-разному, они мерят разные вещи;
- **порог совпадает с `contamination.threshold`.** Разные пороги в чистке и в
  проверке ловили бы не контаминацию, а разницу порогов: пара с Жаккаром между
  двумя порогами проходит очистку законно и потом всплывает в проверке.

Жадный проход даёт ещё и гарантию: среди выживших не остаётся ни одной пары
выше порога, значит, и между train и test её быть не может.

**Подтверждение.**

```
2. Дедупликация ловит не только буквальные повторы
  ✓ точный дубль удалён (dropped_exact_dup = 1)
  ✓ почти-дубль удалён (dropped_near_dup = 1)
  ✓ телефон, почта и дата рождения замаскированы (совпадений 3)
```

## Дефект 5. Гейт разнообразия был отчётом

**В чём был.** `src/diversity.py` считал всё правильно — и на нарушении писал:

```python
    if failed:
        # TODO: гейт или отчёт?
        print("diversity: предупреждение — " + "; ".join(failed))
```

После чего печатал бодрую сводку и завершался с кодом 0.

**Как проявлялся.** Заведомо вырожденный набор — 1200 строк с одним системным
промптом, одной темой и ответами одной длины — проходит пайплайн целиком.
Схема цела, дублей нет, контаминации нет: вырожденность не свойство строки,
а свойство набора, и ни одна другая стадия её не видит. Обучение на таком
наборе сходится быстрее обычного, и модель выучивает шаблон вместо задачи.

**Как исправлен.** Нарушение порогов поднимает `DiversityError` с перечислением
**всех** нарушенных порогов сразу — чинить по одному за прогон означало бы
N прогонов пайплайна. Метрики пишутся в `metrics/diversity.json` до падения:
разбираться есть по чему. В точке входа исключение превращается в `SystemExit`
с текстом, чтобы в логе было сообщение, а не traceback.

Пороги не трогались ни на шаг: подгонка порога под данные — это тот же дефект,
только замаскированный.

**Подтверждение.**

```
6. Гейт разнообразия падает на вырожденном наборе
  ✓ гейт упал и назвал 4 нарушенных порога — разбираться есть по чему
7. Гейт разнообразия пропускает нормальный датасет
  ✓ diversity: 1810 строк, 5 системных промптов, 89 групп (крупнейшая 1.7%),
    разброс длин p90/p10 = 8.13
```
