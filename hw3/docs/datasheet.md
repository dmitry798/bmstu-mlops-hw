# Datasheet: Python-код по текстовому описанию

## Задача

Генерация Python-кода по формулировке на естественном языке. На вход —
описание задачи и опциональные входные данные, на выход — реализация на Python.

Формат хранения — chat JSONL, одна строка на пример:

```json
{"id": "...", "topic": "...", "messages": [
  {"role": "system", "content": "..."},
  {"role": "user", "content": "..."},
  {"role": "assistant", "content": "..."}]}
```

## Источник

| | |
| --- | --- |
| Датасет | [`iamtarun/python_code_instructions_18k_alpaca`](https://huggingface.co/datasets/iamtarun/python_code_instructions_18k_alpaca) |
| Объём источника | 18 612 строк, ~11,4 МБ |
| Колонки | `instruction`, `input`, `output`, `prompt` |
| Сплиты в источнике | только `train` |
| Формат | alpaca (инструкция + опциональный вход + ответ) |
| Как получен | `scripts/fetch_dataset.py` — загрузка parquet с HF и нарезка на два шарда |

**Лицензия.** На карточке датасета лицензия явно не указана. Набор собран
в стиле Stanford Alpaca и производных от него инструктивных корпусов;
использование здесь — учебное, некоммерческое, в рамках домашней работы,
с указанием авторства. Перед любым коммерческим применением лицензионный
статус нужно уточнять у автора набора: отсутствие лицензии — это не
«разрешено всё», а «не разрешено ничего сверх добросовестного использования».
Сам источник в репозиторий не коммитится (см. `.gitignore`), распространяется
только код, который его воспроизводит.

**Происхождение данных.** Набор синтетический по происхождению: инструкции
и решения сгенерированы языковой моделью, а не собраны у людей. Отсюда
большинство ограничений в конце этого документа.

## Что сделано с источником

Скачанный чужой набор — сырьё. Стадия `collect` не перекладывает parquet
в JSONL один в один; каждое действие видно числом в `metrics/collect.json`.

| Действие | Параметр | Зачем | Счётчик |
| --- | --- | --- | --- |
| **Разметка темой** | `src/topics.py` | В источнике поля темы нет вообще. Без него нечем делать ни групповой сплит, ни гейт разнообразия | `topics_kept`, `dropped_untagged` |
| **Сверка ответа с реальностью** | `collect.verify_output_syntax` | Ответ здесь — код, и он обязан разбираться `ast.parse`. Часть примеров в источнике обрезана или синтаксически битая. Чужую разметку не принимаем на веру | `dropped_answer_mismatch` |
| **Снятие markdown-обрамления** | `collect.strip_code_fences` | ```` ```python ```` в целевом тексте — шум, который модель заучит как часть ответа | `code_fences_stripped` |
| **Балансировка по темам** | `collect.max_per_topic` | Без неё крупнейшая тема решает за весь датасет и пробивает `diversity.max_group_share` | `dropped_over_topic_cap`, `largest_topic_share` |
| **Разведение инструкции** | `collect.system_prompts` | В источнике инструкция-обёртка одна на все 18k строк. Модель, обученная на одной формулировке, заучивает её как константу и ломается от перефраза. Вариант выбирается детерминированно, по `sha1(id)` | `system_prompt_variants` |
| **Дедупликация по содержимому** | `id = sha1(instruction, input, output)` | В источнике нет поля `id`; хэш содержимого ловит побайтовые повторы между шардами | `dropped_duplicate_id` |

### Про темы отдельно

Тема выводится из текста задания и кода упорядоченной таксономией
(`src/topics.py`, ~90 правил): сначала узкие алгоритмические задачи
(ханойские башни, Фибоначчи), затем библиотеки (pandas, Flask, PyTorch),
затем конструкции языка (декораторы, генераторы), затем широкие домены.
Строка получает лейбл первого сработавшего правила.

Строка, не попавшая ни под одно правило, **выбрасывается**
(`collect.drop_untagged`). Корзины «other» здесь нет сознательно: она стала бы
крупнейшей группой, обесценила бы `max_group_share` и, что важнее, сделала бы
групповой сплит бессмысленным — в одной группе оказалось бы всё подряд.

Тема — это ключ группового сплита, а не украшение. Её качество определяет,
честен ли `test`.

## Версии

| Версия | Состав | Смысл |
| --- | --- | --- |
| `v1` | шард `data/source/0000.parquet` — половина источника | базовая |
| `v2` | оба шарда — источник целиком | расширенная |

Шарды делятся не по порядку строк, а по хэшу содержимого: иначе состав тем
в шардах оказался бы разным, и разница v1 → v2 показывала бы «данные стали
другими» вместо «данных стало больше». Деление воспроизводимо побайтово:
после повторного `make fetch` на уже собранном пайплайне `dvc repro` отвечает
`Stage 'collect' didn't change` — шарды пересобрались теми же самыми.

Размер шардов: 9252 и 9360 строк (сумма — 18 612, весь источник).

Переключение: `make v1` / `make v2`. Разница: `make diff`
(`dvc metrics diff`). Версия живёт в `params.yaml` → `collect.version`,
и стадия `collect` объявлена от неё зависимой (см. `docs/defects.md`, дефект 2).

Разница между версиями (`make diff`, сокращённо — только содержательные строки):

| Метрика | v1 | v2 | Δ |
| --- | --- | --- | --- |
| `collect.files` | 1 | 2 | +1 |
| `collect.rows_scanned` | 9 252 | 18 612 | +9 360 |
| `collect.rows_written` | 1 812 | 2 184 | +372 |
| `collect.dropped_answer_mismatch` | 1 097 | 2 217 | +1 120 |
| `collect.dropped_untagged` | 606 | 1 189 | +583 |
| `collect.dropped_over_topic_cap` | 5 737 | 13 022 | +7 285 |
| `collect.largest_topic_share` | 0,0166 | 0,0137 | −0,0029 |
| `clean.rows_out` | 1 810 | 2 174 | +364 |
| `clean.dropped_exact_dup` | 2 | 5 | +3 |
| `clean.dropped_near_dup` | 0 | 3 | +3 |
| `clean.pii_rows_masked` | 33 | 45 | +12 |
| `diversity.examples` | 1 810 | 2 174 | +364 |
| `diversity.answer_len.ratio_p90_p10` | 8,13 | 8,67 | +0,54 |
| `split.sizes.train / val / test` | 1448 / 181 / 181 | 1739 / 218 / 217 | — |

Что здесь стоит прочитать, кроме «стало больше»:

- **Рост в 2 раза по источнику даёт +20% по датасету** (1 812 → 2 184).
  Виноват `max_per_topic`: темы, уже упёршиеся в потолок 30, из второго шарда
  не берут ничего. Прирост дали только редкие темы. Это ожидаемое поведение
  балансировки, а не потеря данных.
- **Доля крупнейшей темы упала** (1,66% → 1,37%): набор стал ровнее.
- **`dropped_near_dup` вырос с 0 до 3.** На одном шарде почти-дублей
  не нашлось, на двух — появились: одинаковые задачи разъехались по шардам
  и встретились только в v2. Ровно тот случай, ради которого near-dup
  дедупликация и нужна; точный хэш поймал из них только часть
  (`dropped_exact_dup` 2 → 5).

## Очистка

Порядок стадий: **схема → длины → ПДн → точная дедупликация → near-dup**.
Порядок не косметический, обоснование — в `docs/defects.md`, дефект 4.

| Шаг | Параметры | Метрика |
| --- | --- | --- |
| Валидация схемы | `src/schema.py` (pydantic, `extra="forbid"`, роли ровно `system, user, assistant`) | падение с номером строки |
| Фильтр длин | `clean.min_user_chars`=30, `max_user_chars`=4000, `min_assistant_chars`=5 | `dropped_length` |
| ПДн | `clean.pii.enabled` | `pii_hits`, `pii_rows_masked` |
| Точная дедупликация | по `normalize_text(user)` | `dropped_exact_dup` — 2 (v1) / 5 (v2) |
| Near-dup | шингл 4 слова, 64 перестановки, Жаккар ≥ 0,85 | `dropped_near_dup` — 0 (v1) / 3 (v2) |

**Про ПДн.** Счётчики оказались **не** нулевыми: на v1 замаскировано
68 адресов электронной почты в 33 строках, на v2 — 93 в 45 строках.
Телефонов и дат рождения не найдено. Почти все находки — примеры вида
`john@example.com` в задачах на валидацию e-mail и на отправку писем,
то есть заведомо вымышленные адреса. Маскировать их всё равно правильно:
модель не должна выучивать конкретный адрес как часть шаблона ответа,
а отличать вымышленный адрес от настоящего автоматически нечем.
Стадия обязательна в любом случае:
ноль, полученный проверкой, — результат; ноль, полученный отсутствием
проверки, — надежда. Маскируются телефон, e-mail и дата рождения рядом
с маркером рождения (голый `dd.mm.yyyy` не маскируется: он выбил бы даты
внутри кода и строковых литералов).

## Сплит

| | |
| --- | --- |
| Доли | train 0,8 / val 0,1 / test 0,1 |
| Ключ группы | `topic` |
| Seed | 42 |
| Алгоритм | группы от крупной к мелкой, каждая — в сплит с наибольшим недобором |

**Почему по группам, а не случайно по строкам.** Внутри одной темы задания —
парафразы друг друга. Случайный сплит раскладывает парафразы по разные
стороны train/test, и метрика на test завышается. Замер с лекции: случайный
сплит — 19,5% утечки, по темам — 12,3%, дедупликация плюс группы — 0.

**Цена решения, названная честно.** Групповой сплит по теме означает, что в
`test` попадают темы, **целиком не виденные** в обучении. Это более строгая
проверка, чем «новая задача из знакомой темы», и абсолютные метрики на таком
`test` будут ниже, чем при случайном сплите. Это не недостаток сплита,
а отсутствие завышения: цифра со случайного сплита измеряла бы способность
модели вспомнить парафраз, а не решить задачу.

**Контаминация.** Проверяется по четырём осям — `id`, нормализованный текст,
группа, near-dup пары с тем же порогом 0,85, что в чистке. Требование —
ноль по всем четырём; ненулевое значение роняет и стадию `split`, и отдельный
гейт `scripts/check_contamination.py` (годится для CI).

## Известные ограничения

1. **Синтетическое происхождение.** Инструкции и решения сгенерированы
   языковой моделью. Модель, обученная на этом наборе, учится воспроизводить
   стиль генератора, а не практики живых разработчиков.
2. **Корректность кода не проверена исполнением.** Проверен только синтаксис
   (`ast.parse`) — и отсев на этом оказался крупным: 1 097 примеров на v1
   и 2 217 на v2, около 12% источника, не разбираются как Python вообще.
   Это само по себе характеристика источника: каждый восьмой «готовый»
   пример не является кодом. Код может разбираться и при этом делать не то, что
   просили, или падать в рантайме. Полноценная проверка требует
   исполнения в песочнице с тестами — за рамками ДЗ 3.
3. **Тема выведена эвристикой.** Таксономия по ключевым словам ошибается:
   задача про сортировку словаря может попасть и в «Сортировка», и в
   «Словари», в зависимости от того, чьё правило выше. Для сплита критично
   не абсолютная точность лейбла, а то, что похожие задачи получают
   **одинаковый** лейбл; но часть парафразов с разной лексикой расходится
   по разным группам, и от них страхует уже near-dup дедупликация.
4. **Строки без темы выброшены.** На v1 это 606 строк, на v2 — 1 189
   (около 6,4% источника). Потеря объёма и смещение: выброшены именно те
   задачи, чья лексика не похожа ни на одно правило, то есть нетипичные.
   Датасет смещён в сторону типовых учебных задач.
5. **Балансировка по темам — тоже смещение.** `max_per_topic` обрезает
   крупные темы: отброшено 5 737 строк на v1 и 13 022 на v2 — больше,
   чем осталось. Распределение тем в датасете не отражает распределение
   ни в источнике, ни тем более в реальных запросах. Взамен получен ровный
   набор, где ни одна тема не занимает больше 1,7%.

9. **Есть темы из одного примера.** Медианный размер темы 28, минимальный — 1.
   Такая тема целиком уезжает в один сплит: в обучении её либо нет совсем,
   либо она представлена единственной строкой. На метрики это не влияет
   (таких тем единицы), но при расширении набора имеет смысл добавить
   отсечку по минимальному размеру темы.
6. **Язык.** Инструкции в источнике английские, системный промпт —
   русский. Такая смесь сознательна (задача формулируется по-русски,
   спецификация приходит как есть), но это не «русскоязычный датасет»:
   на чисто русских формулировках поведение не проверено.
7. **Длина.** Примеры короткие: типичный ответ — функция на десяток строк.
   Ни многофайловых задач, ни длинного контекста здесь нет.
8. **Только `train` в источнике.** Val и test нарезаны нами; независимого
   held-out, собранного отдельно от train, у датасета нет.

```bash
uv sync

make repro                               # collect → clean → diversity → split
make check                               # самопроверка, восемь пунктов
```
