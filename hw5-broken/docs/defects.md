# Разбор пяти дефектов hw5-broken

Датасет — свой из ДЗ 3–4: генерация Python-кода по описанию (iamtarun/python_code_instructions_18k_alpaca),
тензоры `data/tokenized/train.pt` (1739 примеров) и `val.pt` (218 примеров) — выход стадии tokenize ДЗ 4.
Железо: NVIDIA RTX 5070 12 ГБ, cuda, bfloat16. Эпоха — 217 шагов оптимизатора (эффективный батч 8).

Числа «до» сняты в копии проекта, где возвращался ровно один дефект; числа «после» — из `metrics/train_*.json`
финального `make train`.

## 1. Нет валидации — обучение вслепую

**В чём был.** В `src/train.py` `base_val = None` (с TODO), функция `evaluate` нигде не вызывалась, `curve_val` оставался пустым.

**Как проявлялся.** В логе только train loss; `base_val_loss` и `final_val_loss` в метриках — `null`. Нельзя сказать,
лучше ли адаптер базовой модели и не переобучается ли он: train loss по шагам скачет от 0,43 до 0,80 из-за разной длины батчей.

**Как исправлен.** Перед первым шагом считается val loss (шаг 0 = базовая модель, т.к. LoRA-матрица B инициализирована нулями),
затем каждые `eval_every: 10` шагов и на последнем шаге. Время оценки идёт в `eval_seconds` и не входит в `seconds`.

**Чем подтверждается.** В `curve_val` 22 точки: val loss базовой модели **1,026** → **0,7923** на 10-м шаге → **0,7026** в конце эпохи.
Падение монотонное, без взлётов, то есть адаптер учит задачу, а не запоминает train.

## 2. Слишком большой learning rate

**В чём был.** `params.yaml → train.lr: 1.0e-2`. Для LoRA с alpha/r = 2 это в 50 раз выше разумного.

**Как проявлялся.** Прогон all_layers с lr=1e-2: train loss на первых шагах 1,14 → **32,39** (максимум), к шагу 20 — 10,96,
в конце эпохи ~**6,8**, т.е. в 6 раз выше начального. Val loss **1,010 → 6,78** — адаптер хуже базовой модели в 6,7 раза.

**Как исправлен.** `lr: 2.0e-4` — стандартное значение для LoRA r=8 с косинусным расписанием и warmup.

**Чем подтверждается.** Train loss ни разу не поднялся выше стартового (максимум 1,18), val loss 1,026 → **0,7026** (−31,5 %).

## 3. Заморозка 14 слоёв не работала

**В чём был.** `lora_config()` принимал `n_layers` и `freeze_first`, но не передавал их в `LoraConfig` — параметра
`layers_to_transform` не было, адаптеры навешивались на все 28 слоёв в обоих вариантах.

**Как проявлялся.** Вариант freeze14 до исправления: обучаемых **5 046 272** — ровно как у all_layers, адаптер те же 30,2 МБ,
`layers_to_transform` в `adapter_config.json` = `null`. Отсюда ложный вывод «заморозка бесполезна».

**Как исправлен.** `layers_to_transform=list(range(freeze_first, n_layers))` при `freeze_first > 0`.

**Чем подтверждается.**

| | all_layers | freeze14 |
|---|---|---|
| обучаемых параметров | 5 046 272 (0,84 %) | **2 523 136** (0,42 %) |
| время обучения | 145,7 с | **112,4 с** |
| пик памяти (cuda) | 1283 МБ | 1244 МБ |
| val loss в конце | 0,7026 | 0,7247 |
| `adapter_model.safetensors` | 20,2 МБ | 10,1 МБ |

Заморозка вдвое сокращает параметры и на 23 % время ценой +0,022 val loss.

## 4. Адаптер не поднимается у товарища

**В чём был.** `train.py` сохранял только `save_pretrained` модели — без токенизатора; `src/compare.py` брал токенизатор
не из папки адаптера, а по имени модели из `params.yaml`.

**Как проявлялся.** У автора `make compare` работает (есть `params.yaml` и кеш HF). У получателя папки адаптера нет ни
токенизатора, ни шаблона чата (`enable_thinking: false`): офлайн загрузка падает, а с другим шаблоном ответы были бы другими.
В папке лежали только `adapter_model.safetensors`, `adapter_config.json`, `README.md` — **20,2 МБ**.

**Как исправлен.** `tokenizer.save_pretrained(adapter_dir)` после сохранения адаптера; `load_adapter_tokenizer()` в compare
читает токенизатор из `adapter_dir`.

**Чем подтверждается.** В папке появились `tokenizer.json`, `tokenizer_config.json`, `chat_template.jinja`, папка — **30,2 МБ**.
Проверка 4 `make check` копирует папку в песочницу и с `HF_HUB_OFFLINE=1` получает 5 из 5 дословно совпавших ответов.

## 5. Прогоны невоспроизводимы

**В чём был.** В `src/runtime.py` есть `set_seed()`, но `train.py` его не вызывал. Инициализация матриц A в LoRA и
маски dropout брались из случайного состояния torch.

**Как проявлялся.** Два прогона по 3 шага с одним конфигом до исправления: `[1.1407, 1.0725, 1.0864]` и
`[1.1407, 1.0725, 1.0935]` (первые шаги совпадают только потому, что B = 0, и модель на них ещё равна базовой).
Второй слой той же проблемы, специфичный для cuda: даже с сидом кривые были `[…, 1.0896]` vs `[…, 1.0903]` —
backward memory-efficient attention (SDPA) и cuBLAS по умолчанию недетерминированы.

**Как исправлен.** `set_seed(train.seed)` в начале `main()`, до загрузки модели и `get_peft_model`. В сам `set_seed` добавлены
`CUBLAS_WORKSPACE_CONFIG=:4096:8`, `cudnn.deterministic=True` и `torch.use_deterministic_algorithms(True)`.

**Чем подтверждается.** Проверка 5 `make check`: два прогона дают одинаковую кривую `[1.1407, 1.0725, 1.0887]`.
